## 一、先理解项目和当前任务

若用户交付的是最新的 **182 题 hit@1 逐题归因**，主任务书是 `docs/TASK_V43_EC298_HIT1_ATTRIBUTION.md`。应核对 `docs/EC298_PHASE_A_REPORT.md`、`docs/EC298_PHASE_A_REVIEW.md`、`docs/EC298_PHASE_B_REVIEW.md`、`docs/EC298_PHASE_C_REPORT.md`。若用户交付的是 Phase B/C/D 修复，按该阶段任务书 §验收逐条审，不要用另一阶段的自测覆盖当前门槛。

## 二、我们采用的 review 工作方式

1. **先固定被审对象。** 记下 `git rev-parse HEAD`、`git status --short`、相关文件 SHA、实施者声称的提交范围、测试环境和交付目录。这个仓库的 Phase B/C 改动曾同时存在于共享工作树，交接时 `HEAD=5c8f284` 且仍有很多未提交变更；不能把全仓现状误认成 Phase B 的独立提交。不要用 `git clean/reset/checkout` 清理他人的改动。
2. **任务书逐条对照。** 把每项要求判为通过、阻断、证据不足或不在本轮范围。核对真实工作流连接：检索卡 → PredictionTask → 模型响应/AtomTool → validation → report adjudication → ReactionEvent → export。只看单个纯函数或报告摘要不够；尤其要检查选中卡、未选中卡、崩溃恢复和导出验证这些不同入口是否使用同一门禁。
3. **独立复现关键数字。** 对正式分数、题数、模式分布、调用账、资产清单、产物哈希与 TSV/JSON 逐题关系，用原始封存件或受保护清单重新计算。实施者写“全绿”“与清单一致”只是待核验陈述。优先做能推翻结论的最小反例，再跑相关测试；有具体剩余风险时才扩大全仓测试。记录自己运行的命令和结果，清楚区分“我独立运行”与“实施者报告”。
4. **用真实失败路径判断严重度。** 若发现疑似 bug，构造最小夹具并走完整路径，展示输入、落盘 artifact、最终裁决/事件/导出结果。Phase B R1 就用「两张合格 recorded + 一张异底物脏卡」证明脏卡能被模型选中并提交；测试全绿并没有否定该反例。复现请放临时目录，避免污染封存 run 和共享树。
5. **区分事实层级与因果推断。** 原始检索含金标 → 任务候选含金标 → 被选中 → 验证通过/可报告 → 实际报告，是不同层。下层成立不自动推出上层。模型弃答、AtomTool 拒绝、产物不等于金标，是可观察结果；“模型化学推理错”“数据库没有反应”“本可答对”需要额外资格证据。未知就写 `unknown` 和缺口，不能凑主因标签。
6. **区分结构修复与准确率收益。** Phase B 的未选中候选进入第 2–5 位，主要影响 @3/@5；其 `selected` 仍在第 1 位，不能宣称已经提升 @1。Phase C 的旧 66 题 23/43 路由再分类只是离线模拟，不是新模型命中率；门禁测试通过也不等于化学预测正确。真实模型 dev 对照未执行就写 `not_measured`。已见 298 上的修复复跑只能叫 `post_hoc_repair_check`，不能冒充新盲测。
7. **保持封存和研究边界。** EC298 首跑 run、金标、Phase A 输入清单和资产 SHA 是审计基线；归因与评分可只读访问金标，预测/检索/提示词/策略绝不能读取。不得为补缺文件重跑引擎或调用付费 API；不得用已见 298 选供体、阈值、预算或调 prompt。输入缺失/哈希不符时报告阻断，不用新结果冒充首跑。禁止把 API key、远端私密路径写进 review 文档。
8. **检查确定性与可追溯性。** 对 task ID、run identity、版本、资产来源 SHA、验证引用、报告 rank、事件引用、输出哈希做闭环。改一个输入字节、删一个必需字段、错指另一父路径或旧 schema 混入时应 fail-closed。硬杀恢复须比较最终账本、裁决、调用账和不可变产物，不只确认进程能继续。

## 三、各阶段的高价值审查点

- **Phase B：** 同底物、精确匹配、方向、条件资格应在任务候选和最终选中验证中一致；`selected` 与未选中卡都要能回到不可变 validation 文件及 payload SHA；`in_task`、`in_model_order`、`selected`、`card_eligible` 各自独立；`reportable`、`committed`、`expand_selected` 的蕴含关系和跨父路径隔离需核验；v2 导出缺裁决指纹必须拒绝，v1 兼容只在真正 v1 时适用；崩溃点重放不得多耗模型调用或改变账本。
- **Phase C：** `mapping_status=resolved` 不等于当前底物适用；核查供体反应变化是否从真实映射提取、反应中心及邻域/键级/氢/价态/电荷检查是否执行、多个对齐是否产生不同目标并正确标 `ambiguous`。不要从未映射区猜反应，不要放宽 `bond_already_present`，键级变化走显式 `change_bond_order`。核查 AtomTool 的操作顺序执行与最终目标图对账，不接受只要目标 MoleCode 可解析就算成功。对旧 66 题 23/43 的分流应按 qid 复核；供体预算评估顺序曾导致 11→23 的伪差异，检查当前次序与计数口径。
- **类比历史数字冲突：** 旧 R2 曾写 23 条被拒目标中 8 条直接匹配金标；Phase C 报告称四种口径均为 0/23。不要继承任何一方；从封存目标字符串、同一金标和明确身份函数独立重算，给逐题差异与口径说明。此项也写入 hit@1 归因任务书。
- **182 题 hit@1 归因：** 必须恰好 182 个唯一 qid，48+43+66+25 对平，首位未中但 rank 2–5 命中的 14 题逐题可回查。每条非 `unknown` 断点有同一 run/qid/path 的证据引用。唯一 recorded 的 48 题无模型选择，不能标模型选错；多 recorded 中「任务候选含金标」还需与「合格可报告」分开；类比 28 弃答/23 拒绝/15 接纳都未命中，但不同故障不能合并；novel 的 25 题不能叫真正零检索证据。验证任务书规定的负例测试：原始检索含金标却未进任务、异底物脏卡、跨父串线、可解析目标并非金标、rank 2 正确但 rank 1 错、文件缺失/哈希变化。
- **Phase D：** 只有在真的交付后才审。供体按反应物相似度找回、资产重映射、预算选择都须在冻结 dev 上定值；不得把旧 298 的 budget=10 诊断 30/66 直接当参数依据。化学门禁和竞争歧义弃权不能为提高覆盖率而放宽。

## 四、review 输出格式与判定纪律

给用户的结论先写 **通过 / 暂不通过 / 范围内通过但效果未测**，附精确审查对象的 commit、工作树状态和时间点。按严重度列发现：`P1` 为可能产生错误报告/提交、证据越层、金标泄漏、封存被改或恢复分歧；`P2` 为追溯、统计或新鲜度门禁失真；文案问题单列。每条发现要给：可复现输入/命令、观察到的结果、期望、影响范围、代码与产物位置、最小修复门槛、应新增的失败回归。不要只说“可能有问题”。

同时列出**已独立通过的检查**与**未验证的限制**，不因一个阻断项否认其它已证实成果。修复回轮时逐条核对旧 review，标出通过/未闭环/新发现；保留历史判定，不把旧失败记录删掉。报告中不要写超出证据的整体性能结论；凡称“提升 @1”，须有同模型、同输入、同评分口径的冻结 dev 或新外考成对对照，并披露成本/调用差异。

如需记录到仓库，命名为 `docs/<阶段>_REVIEW.md`，在文首注明 R1/R2、审查快照和最终状态。向用户用简洁中文说明阻断项、证据和下一步修复门槛；不要替实施者做修复。用户若给出新修复交付，主动进入下一轮复核。

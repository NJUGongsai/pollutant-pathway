## 0. 我们在做什么（一段话说清）

给定一个**底物分子**，系统要预测它被酶催化后生成什么产物（反应式）。系统流程：

```
候选池构建（从反应模板库检索相似反应 → 编译成可执行候选，每题约 2-8 条）
   → 模型看到候选池，选出/提出反应（写成原子级编辑协议）
   → 执行器照做，得到产物
   → 判分：与标准答案（参考图）比对
```

评测集 298 道题（**已见题**，post-hoc，不可外推）。当前一次全量跑批约 50 分钟、约 4M tokens。

## 1. 三个待裁定改动

### 改动 A：判分口径从「参与物恰好相等」改为「主产物全部命中 + 底物命中」

**现状（实测事实）**：

| 项 | 值 |
|---|---|
| 标准答案的参与物声明状态 | **298/298 条全部标记为 `partial`（声明不完整）** |
| 标准答案声明的角色 | 只有 `substrate`（1 个/题）+ `principal_product`（共 347 个，1-3 个/题） |
| 标准答案声明里有没有水/辅因子/副产物 | **一条都没有** |
| 判分条件（代码） | 模型事件的参与物集合必须与标准答案声明**恰好相等**；多写 = `superset`，少写 = `partial_subset`，**两者都不算对** |
| 同系统内的另一个模块（审计） | 看到 `partial` 声明时，参与物完整度判 **`CHECK_UNKNOWN`（未知）**，即"我不知道完整清单" |

**由此产生的矛盾**：审计模块说"这份清单不完整"，判分模块却要求"模型必须跟它一模一样"。

**实测影响（298 题一次批）**：

| 类别 | 题数 |
|---|---|
| 现判对（strict） | 119 |
| **主产物全部命中、仅因多写参与物被判半对** | **35-37**（两个口径差 2 题） |
| 主产物身份不对（真错） | 129（其中 104 题连分子骨架都不同、25 题骨架同但立体/电荷不同） |
| 事件未提交（跑失败） | 6 |

**提议**：新判据 `criteria-v3`——只要「标准答案声明的**全部 principal_product** 都出现在模型事件的产物侧（分子身份严格相等）」且「题目给的底物出现在反应物侧」，即判对；
**不再要求参与物集合相等**（多写水/辅因子/副产物不算错，少写其它参与物也不扣）。

**预期（已实测，零成本重放，非估算）**：

| 指标 | 现判法 v2 | 新判法 v3 | 变化 |
|---|---:|---:|---:|
| strict（答对） | 119（39.9%） | **156（52.35%）** | +37 |
| **hit@1（排第一才算）** | 86（28.9%） | **109（36.58%）** | **+23** |
| hit@3 | 112 | 148（49.7%） | +36 |
| 半对（partial） | 39 | 2 | −37 |
| 完全不对 | 140 | 140 | 0 |

37 题转正、**0 题变差、0 题位次退化**。重放对基线逐题复现 298/298（86/112/119、119/39/140）。
**注意：这是判据修正后的口径上限，模型输出一字未变；化学正确性尚未评审。**

**旧读数处理**：v1/v2 结果一字不改；v3 单独一列；历史批次用 v3 重算后双列对照。

### 改动 B：池条目新增 `reaction_type` 人话字段

**现状**：模型看到的候选条目长这样（真实结构，已脱敏）：

```
product_smiles: "<产物 SMILES>"
coproducts: []
transformation_ref: "bt0014#r0282"        ← 库记录编号，模型看不懂
evidence.edit_summary: {"n_edits":1, "op_counts":{"add_atom":1},
                        "added_atoms":[{"element":"O"}]}   ← "加 1 个氧原子"
```

**没有任何人类语言的反应类型**。"加 1 个氧 = 羟基化"这层语义**完全由模型自己推**。

**提议**：保留 `transformation_ref`（溯源性，且它参与候选身份哈希）；**新增** `reaction_type` 字段写人话（如「羟基化」「水解」「脱羧」），pool 渲染时两个都给模型看。反应类型由 LLM 对 531 条候选批量命名（两级口径：一级类 + 二级说明，低置信标注）。

---

### 改动 C：池前新增一个 Agent（混合模式）

**想法**：在候选池构建后、模型决策前，插入一个 agent：

```
底物 + 检索到的相似反应（原始候选）
   → agent 筛选/重写，输出 5 条最靠谱的反应入池
   → 每条附 evidence + reaction_type
   → 标注来源：from_database（来自检索候选）/ synthesized（agent 自己写）
```

- **模式**：混合——优先从候选里挑；候选都不靠谱时允许自己写新反应
- **模型**：DeepSeek（与跑批同模型），每题 1 次调用，298 题约 0.5-1M tokens
- **验证方式**：单臂直上（不做 A/B 两臂对照）

## 2. 已知的技术风险（请求方自己识别出的，请复核并补充）

| # | 风险 | 已知证据 |
|---|---|---|
| R1 | **agent 自己写的反应不可执行**：候选必须携带「原子级编辑协议」才能被执行器做出产物。我们实测：把参考反应自动转成编辑协议，**只有 8.6%** 能生成可执行且产物正确的协议（原因是原子映射存在化学歧义、协议无删原子操作、参考声明本身不全） | 140 道失分题实测 EXACT 12 / PARTIAL 34 / FAIL 94 |
| R2 | **判据放宽诱发退化**：模型可能学会"只写主产物不写参与物"，化学上更差却拿满分 | 未验证 |
| R3 | **reaction_type 的捷径效应**：若名字由 LLM 生成，模型可能"看名字选"而非自己推理；名字起错会误导 | 未验证 |
| R4 | **单臂直上无法归因**：改动 A（判据）与改动 C（池）同时生效，涨跌无法拆分 | 方法学问题 |
| R5 | **两套代码分叉**：判据改动在 `evaluation.py`，池改动在 builder/compiler，需要合并 | 工程风险 |

## 3. 请裁定（逐条回答，结论 + 理由 + 风险等级）

**Q1** 改动 A 的判据（主产物全中 + 底物中 ⇒ 判对，忽略参与物）在化学与评测学上是否站得住？
有没有把"真错"判成对的系统性风险？（已知：129 道真错里 104 道的产物骨架就不同，理论上不受影响）

**Q2** 改动 A 会不会诱导模型退化（只写主产物、不写完整反应式）？如果会，是否需要在判据里保留某种"完整性激励"（例如：完整性作为独立披露指标而非判对条件）？

**Q3** 改动 B（reaction_type 人话）值得做吗？捷径风险（R3）如何评估与缓解？是否应先做小样本对照（同模型、同池，仅加不加人话字段）再全量？

**Q4** 改动 C 的混合模式（先挑后写 + 来源标记）可行吗？R1（8.6% 可执行率）是不是致命阻碍？如果要求"agent 写的新反应必须先过可执行性干跑校验（不可执行即丢弃）"，这个门够不够？

**Q5** 三项改动的**顺序**：一次全上，还是分三步（先改判据重算 → 再加 reaction_type 跑一批 → 再上 agent）？哪个对科学结论更有利？请给出你认为的最小可归因方案。

**Q6** 有没有更简单的替代方案，能拿到同样的信息？（例如：不改池、只改判据 + 把参与物完整性作为独立披露；或只做 reaction_type 不做 agent）

**Q7（由实测新增）** 新判法下出现一个新的结构性反差：**答对 156 题，但只有 109 题排在第一位——47 题"答得对但没选对位"。**
这是否意味着：下一步的主要杠杆已从"生成/池质量"转向"排序/位次"？
若是，改动 C（pool agent）应当定位为 **rerank**（从候选里重排，收益打这 47 题）而不是 **生成新反应**（收益未知、且有 R1 可执行性风险）？请明确你推荐的定位，以及两者的预期收益差异。

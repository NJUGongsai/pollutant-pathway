# EC298 首跑独立复核 R2：低分归因与修复顺序

**审查对象**：`docs/EC298_REPORT.md`、`docs/EC298_REVIEW.md`、Chenyu 封存的 `runs/ec298_v43r1/` 原始答卷，以及本仓评分、路由、预测和导出代码。  
**范围**：只读重算与架构 review；不改首跑答卷，不使用 298 题金标调参。  
**结论**：首份报告把引擎成绩算低了；修正后 agent 在 hit@5 落后引擎 **63/298 题**。主要损失来自“只报告已选中的一次事件”和当前类比路线，而不是 5 次 API 失败或单一 AtomTool 拒绝规则。

## 1. 先修正测量口径

上一轮 review 对两处评分问题的判断成立。`exam.py` 对 agent 候选从原始 SMILES 计算 `cn_identity`，对引擎候选却直接使用缓存的 `product_identity`；两臂与金标并非同一身份口径。以封存原始候选的 SMILES 对两臂统一计算 `cn_identity`，并沿用当前“完整候选字符串匹配任一金标组分”的规则，得到：

| hit@K | Agent | 引擎 Top-10 | Agent − 引擎 |
|---|---:|---:|---:|
| @1 | 116 | 118 | −2 |
| @3 | 128 | 174 | −46 |
| @5 | 130 | 193 | **−63** |
| @10 | 130* | 209 | −79* |

\* Agent 最多报告五个产物，@10 不是对等比较。原报告的引擎 82/117/135/153 及“Agent @1 +34 题”不成立。该错误解释了**报告为什么看起来较好**，并不解释 agent 为何只命中 130 题。

另有 18 条 agent 候选含 `.`，当前 scorer 将整条多组分 SMILES 对单个金标组分。仅作敏感性分析：若每条候选的任一组分命中即可，agent @1/@3/@5 为 129/141/143，引擎为 132/184/199，@5 差距仍为 −56。正式发布前必须先冻结多组分规则，再对两臂同法重评；此处的组分数字不是正式成绩。

“完整候选池”诊断也不能沿用：`_engine_chunk` 只调用 `top_k=10` 并从返回的十条填 `pool_identities`。现有数据只能判断 Top-10 内外，不能判断完整池中是否有金标。

作为交叉核对，修正后的新引擎 @1/@3/@5/@10 为 118/174/193/209；历史 v4.1 引擎为 118/172/190/208，汇总值接近，但逐题首个命中 rank 仍有 24 题不同。不能宣称两个引擎完全相同，也不能再用原报告的 153 对 208 推断新引擎 Top-10 大幅退化。

## 2. 63 题差距在哪里产生

以下为同一整条候选 `cn_identity` 口径的逐题配对重算。`agent@5` 和 `engine@5` 均以 298 题同一金标判定；模式来自封存的逐题运行产物。

| 实际分支与结局 | 题数 | Agent @1 | Agent @5 | 引擎 @1 | 引擎 @5 | @5 差额 |
|---|---:|---:|---:|---:|---:|---:|
| 唯一 recorded，直接提交 | 112 | 64 | 64 | 64 | 86 | −22 |
| 多 recorded，模型选一个 | 70 | 27 | 27 | 27 | 54 | −27 |
| 类比编辑：弃答 | 28 | 0 | 0 | 7 | 14 | −14 |
| 类比编辑：提案被拒 | 23 | 0 | 0 | 1 | 6 | −6 |
| 类比编辑：提案接纳 | 15 | 0 | 0 | 4 | 9 | −9 |
| 新提案：接纳 | 50 | 25 | 39 | 15 | 24 | +15 |
| **合计** | **298** | **116** | **130** | **118** | **193** | **−63** |

类比三行合计 66 题，agent **0/66**；引擎 29/66。唯一 recorded 与多 recorded 合计损失 49 题。新提案分支则净增 15 题。逐题配对看，recorded 两组和类比组没有 agent 独有的 @5 命中；所有 agent 独有命中均来自新提案分支。

输出宽度为 **0 个 51 题、1 个 197 题、2 个 1 题、3 个 1 题、4 个 5 题、5 个 43 题**。197 题只报一个产物，直接限制了 @3/@5。即使以后修好评分，现有输出契约也无法充分表达“按证据强弱报告五条候选，但只沿最可信分支继续展开”的研究设计。

## 3. 第一主因：报告候选与已提交事件被绑在一起

任务书 [`TASK_V43_EXPORT_DEV.md`](TASK_V43_EXPORT_DEV.md) §1 明确要求：可报告候选有独立不可变的裁决账本；最多五个；只有选入 frontier 的产物继续展开。实际实现只对**被选中的一张证据卡**的产物生成 `report_adjudication`：[`nodes.py`](../src/pathway_v43/workflow/nodes.py) 的 `_report_adjudication_payload` 将每条 entry 的 `evidence_id` 固定为该卡，并按该事件的产物位置排 report_rank。导出器 [`export_v3.py`](../src/pathway_v43/output/export_v3.py) 又要求可报告产物列表与已提交 ReactionEvent 的产物逐位相同。这样，多条互斥反应证据无法成为“已验证、可报告、暂不展开”的并列假设。

在 70 道多 recorded 题中，模型均返回排序 `order`，且提交选择等于 `order[0]`。模型输出的排序没有转为可报告的其余候选：只有首选反应进入路径。首选命中 27/70；任意 recorded 反应候选含金标 49/70，金标出现在未选中 recorded 卡上的有 25/70。直接拿模型 `order` 的前五个产物做**未验证诊断**可到 53/70，说明有明显信息在选择后丢失；它不能当作正式 agent 成绩，因为其余卡尚未逐条通过报告门禁。

112 道唯一 recorded 题同样只报告该事件，agent @5 64/112，而引擎 Top-5 86/112。那 22 道引擎独有命中提示其它候选可能有价值，但它们的证据级别和有效性须先核实，不能直接把引擎 Top-5 倒灌为 agent 答案。修复目标是保留 exact recorded 的最高优先级，同时对其它来源的候选逐条验证、标来源、排置信度，允许“报告但不展开”。

## 4. 第二主因：类比路线的 `resolved` 不等于反应适用

[`policy.py`](../src/pathway_v43/domain/policy.py) 只要找到一条 `mapping_status == resolved` 的预测证据，就优先走 `analogy_edit`；[`prediction.py`](../src/pathway_v43/services/prediction.py) 只取检索排序第一条 resolved 卡。[`atom_tool.py`](../src/pathway_v43/services/atom_tool.py) 的 `align_donor_mapping` 可仅用反应中心子图对齐，并取 RDKit 返回的第一个子结构匹配；该步骤没有证明供体反应在目标底物上的邻域、键级变化、氢和价态条件都成立。

66 道类比题中，40 道只对齐 2 或 3 个中心原子。封存任务中，同一“甲醛→甲酸”供体被用于 9 个不同目标；有模型因底物与供体化学环境不符而弃答。原始检索证据的任意卡中有金标的类比题为 59/66，前五张原始卡中有金标为 26/66。这只是**未验证检索覆盖率**，说明路由/选卡值得排查，并不是类比分支可直接取得的分数。

51 条空答已可归为 28 条模型弃答和 23 条编辑拒绝；后者 20 条含 `bond_already_present`，3 条含 `unknown_atom`。键级变化确有协议缺口：现有编辑语言不支持把已存在的单键改成双键。但不能把“23 条被拒”简单算作“23 条本可答对”：22/23 的目标 MoleCode 可解析，**只有 8/23 的目标 SMILES 直接匹配金标**；可解析也不等于目标转化合理。15 条已接纳类比提案同样 0 命中。因此仅放宽 AtomTool 门禁解决不了类比路线。

应先建立供体适用性和映射质量门槛：从带原子映射的供体反应计算真实键/原子变化；核对目标底物的反应中心及一阶邻域、键级、可用氢、价态与变化操作；处理多个等价或竞争匹配；在多供体之间选择，而非拿第一个 `resolved`。无可靠供体时转向已验证规则或受约束新提案。随后给 AtomTool 增加明确的 `change_bond_order` 及逐步状态校验，保持确定性结构门禁。

## 5. 新提案的正收益需要谨慎解释

50 道 `novel_proposal` 中 agent @5 命中 39 道，比引擎的 24 道多 15 道；这是当前唯一显著正收益。该模式的任务书 `candidates=[]`，模型没有直接拿到检索候选产物。但回溯原始检索产物，50 道中 44 道的任意检索卡已含金标；39 道命中中有 34 道在检索证据里也能找到金标。此重叠**不能证明模型抄了检索结果**，也不能支持“完全无证据条件下独立生成”的宣称。现有路由把“映射不可用”归到 novel，掩盖了“有检索产物、但无法映射”这一中间状态；报告需把它单列。

模型调用失败 5 次、最大正常请求在途 33/40，确需按任务书记录，但相对于上述 49+29 道分支损失，不是主要准确率原因。`reasoning_effort=max` 的思考 token 占输出绝大多数，优先属于成本/时延优化议题；目前没有对照实验能证明其导致准确率下降。

## 6. 修复顺序与验收建议

### 阶段 A：先把测量修正，无需再调 API

1. 保留原始答卷、旧 scorer 输出和哈希；另发 scorer v2，从两臂原始 SMILES 统一求 `cn_identity`。先决定多组分计分单位，再同法重算两臂，附逐题配对差异和输入哈希。
2. 将“完整候选池”改名为 Top-10 诊断；如确需覆盖率分档，另做只读全池导出与身份归一化。撤回原报告对完整池和 agent 净增益的结论。
3. 每题诊断至少列出实际模式、报告候选数、证据源、选中/未选中候选、门禁拒因、首个命中 rank。金标只用于离线评估，严禁进入预测任务或检索。

### 阶段 B：修候选裁决架构，优先提升 @3/@5

1. 将“候选是否可报告”与“是否已提交并继续展开”拆成独立状态。对同一父节点的**每张候选证据卡**产生不可变裁决记录，包括原始/规范 SMILES、`evidence_id`、来源等级、确定性验证引用、模型排序位置、`report_rank`、`reportable`、`expand_selected`、拒因。已提交事件只代表被选中展开的路径。
2. `rank_candidates` 的 `order` 经逐卡验证后可形成报告排序；唯一 recorded 也允许把其它已验证候选列在后面。保持 exact known 优先及每父节点最多五个；不把未验证检索卡、被拒结构或模型原文直接导出。
3. 用冻结 dev 集比较候选覆盖、报告宽度、@1/@3/@5 和证据正确率；明确 `@1` 不得因凑宽度丧失 exact known 优先级。298 首跑只作已见试卷的事后诊断，后续改版复跑要标记 post-hoc。

### 阶段 C：重做类比适用性与 AtomTool 编辑协议

1. 用人工审过的“适用/不适用供体”小集钉住反应中心变化、邻域条件和映射唯一性；比较多个供体及 fallback。先在 dev 做关闭当前类比路由的消融，对照 `novel` 或规则路线，确认是否要暂时禁用弱映射。
2. 加入键级变化编辑、顺序执行的图状态校验及目标结构一致性检查；对 23 条拒绝按“目标正确/错误、编辑可执行/不可执行”拆分复核。绝不通过取消 `bond_already_present` 校验来放行。
3. 分别报告类比路由进入率、模型弃答率、编辑拒绝率、接纳提案有效率和命中率，避免用单个 0/66 掩盖不同故障。

### 阶段 D：最后再调模型与成本

在评分、候选报告和映射门槛稳定后，使用 dev 或新封存外考比较 prompt、供体排序和思考预算。真实无证据、映射失败但有候选、以及证据冲突须分别评估。新的 298 分数只能称为**对已见试卷的修复验证**，不能当作新的盲测结论。

**验收判断**：上一轮 review 的评分错误与 Top-10 诊断结论保留；它将 23 条 AtomTool 拒绝列为 P1 主因的权重应下调。当前更优先的 P1 是候选裁决与已提交事件耦合，以及类比路线把弱映射视作可用供体。先改测量，再改候选架构与类比路由，最后优化模型。

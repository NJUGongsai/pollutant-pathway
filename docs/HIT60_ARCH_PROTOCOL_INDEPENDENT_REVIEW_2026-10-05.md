### P2-2：条件匹配逻辑未实现，"未知"标注优于默认假设

## 协议层 vs 架构改变的边界判定

| 组件 | 实际改变内容 | 是否纯协议层 | 需要单独界定的部分 |
|------|------------|------------|------------------|
| C1 | prompt 改为 listwise 排列，复用 E1 解析器 | ✓ 是 | 无 |
| C2（原版） | 候选卡增加字段 | ✓ 是 | novel 路由空转需要补 substrate_profile（新增调用位置） |
| C2（修正版） | 底物档案 + 候选卡字段 | **部分否** | 底物档案需要在 prepare_prediction 调用守恒/官能团检测，是新的执行位置；如果复用 G2，需要明确调用参数与输出端 G2 的差异 |
| C3 | JSON schema 约束 | ✓ 是 | 无 |
| C4 | novel 任务从 candidates=[] 改为带候选列表 | **否** | ① 改变任务语义（从"裸猜"到"在候选中裁决"）；② 新增输入侧 G2 调用（或其他守恒检查）；③ bounded 预算、排序、截断逻辑是新的候选池构造规则 |

**结论**：C1 和 C3 是纯协议层；C2 修正版和 C4 涉及任务组装逻辑改变和新的确定性函数调用位置，应该单独界定为"协议 + 任务组装改进"，不能只标"纯协议层"。

## 推荐的最小工具接入方案及优先级

- 成本：¥1（纯特征提取，无模型调用）

**T2：证据类型标注核查**

- 内容：确认检索系统是否已区分 recorded/rule/analogy/patent，如果未区分则补标注
- 成本：¥0（只读核查）或 ¥2（补标注逻辑）
- 依赖：无
- 理由：C4 候选池构造的前提

- 成本：¥3-5（包含 T1）

### 第三优先级：C4（推演上下文），但需要完整流程披露

  1. 输入侧处理流程审计（P0-3）
  2. 证据类型标注（T2）
  3. 守恒检查结果标注修正（P0-1）

- C1（listwise 排列）：dev 无承载面，等新题卷，¥5

# 第二部分:架构严厉批判(从污染物降解路径预测的根本目标出发)

好，我从**污染物生物降解路径预测**这个核心目标出发，严厉指出架构的根本问题。

---

## 架构的根本错误：你们在做检索系统，不是在做降解路径预测

### 问题 1：知识表示的根本性错误

**污染物降解路径预测的本质是什么？**
- 给定污染物分子 + 微生物代谢环境 → 预测可能的单步酶促反应产物
- 这是**生物化学推理问题**：基于酶的催化机制、底物的官能团、环境条件，推断反应

**你们在做什么？**
- 检索相似反应 → 让 LLM 从记忆里猜常见代谢物 → 事后筛查是否太离谱
- 这是**数据库匹配 + 记忆提取问题**

**证据**：
- 42/48 次调用走 novel 裸猜，`candidates=[]`
- mimo 诊断："模型被迫从'我认识的分子'里挑"
- spurious 36/56：大量输出是"常见代谢物"（苯酚、苯甲酸、CO₂），而非当前底物的化学合理产物

**这是本末倒置**。酶促反应不是"我见过什么分子"，是"这个官能团在这个条件下会发生什么化学变化"。

---

### 问题 2：把推演能力阉割，退化为精确匹配数据库

**F2 资格层的设计错误**：只有"合格 recorded 卡"（完全匹配的已知反应）才能进候选池。

**结果**：
- 36-37/56 金标以**推演形式**在池（USPTO 模板 22 + 类比 10-11 + enviPath 规则 9）
- 这些推演候选被排除在 rank 任务之外
- 系统退化为"我只相信见过的完全一样的反应"

**这违背降解预测的基本需求**：
- **新污染物**不可能有完全匹配的 recorded 反应
- **环境特异性**（不同菌株、不同条件）导致同一污染物的降解路径差异
- **酶的底物宽容性**允许结构相似的底物发生类似反应

**正确的做法**：
- 候选池应包含：实测反应 + 规则推演 + 类比推演 + 化学模板，每种标注证据类型和可信度
- 任务是"从候选池中选择最合理的，或基于化学规则提出新方案"
- 不是"没有完全匹配就让 LLM 裸猜"

---

### 问题 3：路由决策的盲目性——金标在场仍然裸猜

**当前路由逻辑**：
```python
if 合格 recorded ≤ 1 and 类比不适用:
    走 novel 裸猜（candidates=[]）
```

**荒谬之处**：
- 不看池里有没有规则推演产物（enviPath 规则）
- 不看池里有没有类比推演产物（结构相似的底物反应）
- 不看池里有没有专利模板产物（USPTO）
- **金标在检索池 rank 75 位置，系统视而不见，送去 novel 裸猜**

**数据**：
- 11 题金标在 2-5 位，**100% 走 novel**
- 16 题金标在证据池，**12 题被送去 novel**
- 298 侧 unknown 25 题，金标在原始检索层可见但产物链从未出现，其中 3 题引擎排第 1

**这是什么逻辑**？等于医生说"我只认教科书上完全一样的病例，其他都当没见过，凭感觉开药"。

---

### 问题 4：守恒检查的虚假安全感

**你们声称的"守恒检查"**：
- 50 夹具/627 测试验证
- G2 守恒判定器
- "守恒通过"

**实际能力**：
- H/O 是**自由元素**（假设 H₂O/O₂ 隐式供应）
- 只对 C/N/S/P/卤素/金属做精确对账
- TIER_PASS = "**未触发冻结规则**"

**你们缺少的**：
- ❌ 完整反应配平（底物 + 共底物 → 主产物 + 共同产物）
- ❌ 电荷守恒（净电荷平衡）
- ❌ 氧化还原对账（电子守恒、氧化态变化、辅酶 NAD⁺/NADH）
- ❌ 立体化学（手性中心、顺反异构）
- ❌ 反应机制合理性（断键位置、成键位置、中间体稳定性）

**conservation.py:92-94 的注释白纸黑字**：
```python
# 杂原子硬门集合(G2-a/G2-b:N/S/P/卤素/金属;O 与 H 为自由元素,
# 默认隐式供体 {H2O, O2})
```

**化学评审已经指出**（13 行）："这是有限判据筛查，并非完整反应原子映射、所有参与物的质量与电荷配平，也没有完整氧化还原电子账。"

**但你们在原提案里写**："经 50 夹具/627 测试验证的守恒判定器"，**暗示这是充分验证**。

**软件测试数量不能证明化学覆盖度**。627 个测试通过，不代表判据覆盖所有合法酶反应。

**结果**：
- spurious 36/56（dev）：大量化学不合理的产物通过
- "守恒通过"被误解为"化学可行"
- 模型输出无化学约束，随便生成

---

### 问题 5：候选卡信息贫乏，模型无法做化学推理

**模型看到的候选卡**：
```
底物：某个污染物 SMILES
产物：某个代谢物 SMILES
```

**模型看不到的**：
- ❌ 反应类型（氧化？还原？水解？羟基化？）
- ❌ 反应中心（哪个键断？哪个键成？哪个原子被攻击？）
- ❌ 底物匹配度（当前底物有没有这个官能团？）
- ❌ 守恒账本（ΔC、ΔN、ΔO 怎么变的？碎片去哪了？）
- ❌ 条件匹配（需要有氧还是厌氧？pH 范围？辅酶要求？）
- ❌ 证据类型（实测反应？规则推演？类比？专利模板？）
- ❌ 可信度（这个候选有多大把握？）

**结果**：
- 94/162 题（298 题域）"看见没选对"
- 模型无法判断"为什么这个反应可能发生"
- 模型无法判断"这个反应与当前底物是否匹配"
- 排序依靠什么？模型的"语言直觉"？

**mimo 评审点名**（化学评审 85 行）："卡上最该有、但现在没有的字段 = 底物同一性、反应类型、守恒块、可进攻位点"。

---

### 问题 6：证据类型混淆，可信度评估失效

**当前状态**：
- 实测反应（RHEA/BRENDA）、生物规则（enviPath）、跨底物类比、USPTO 专利模板——**未明确区分**
- 同一产物的多个来源可能重复引用同一反应
- USPTO 专利模板未标"生物可行性未知"

**化学意义的巨大差异**：
- **实测反应**：该酶、该底物的真实生物反应，可信度最高
- **生物规则**：从已知反应推广的转化规则，可信度中等，需验证底物匹配
- **跨底物类比**：结构相似底物的反应，可信度取决于相似度
- **USPTO 专利**：有机合成反应，可能用化学催化剂，**不保证生物可行**

**不区分的后果**：
- 把化学合成反应当生物降解反应
- 把推演规则当实测事实
- 把重复引用当独立证据
- 模型无法区分高可信度和低可信度候选

**Lowe USPTO 数据集原作者警告**（化学评审 29 行引用）："重复反应多、部分原子映射有误"——这是来源级风险，必须标注。

---

### 问题 7：单步口径不明确，评估混乱

**已知事实**（化学评审 22-23 行）：
- EAWAG Super Rules 可以**合并两条或更多相邻降解规则**
- 单次调用可能代表一段路径（多步）
- EC 分类依据酶催化的整体反应，不等于基元步

**当前状态**：
- 检索产物中哪些是单步、哪些是多步——**未标注**
- step_scope 字段——**缺失**

**问题**：
- 如果把多步路径当单步金标比较，准确率被虚高估计
- 如果单步产物不匹配多步金标，准确率被低估
- **你们不知道系统真正在预测什么**

---

### 问题 8：in-sample 循环的深度泄漏，dev 测试形同自欺

**G2 守恒规则从哪来的**？
- 原提案 56 行承认："编目由 dev 失败案例引导"
- conservation.py 注释："v2 相对 v1 的判据修订...评审 G 节 9 必改"
- 这些修订是看着 dev 的失败模式设计的

**C2/C4 的字段选择从哪来的**？
- mimo 点名"卡上最该有的字段"
- 是因为看到 dev 缺这些字段导致失败
- 字段设计本身包含 dev 信息泄漏

**所有在 dev 上的增益测试都是什么**？
- 在已知答案的题上调参
- 规则是看着答案设计的，测试是看着答案跑的
- **这是 in-sample 循环的定义**

**原提案的认识不足**（150-151 行）：
- "新采样"如果指对 dev 重跑，**仍是 in-sample**（题是同一批）
- "确证只认新题卷"——正确，但新题卷还没有
- **所有 dev 增益都不能作为泛化能力的证据**

**正确认识**：
- dev 上的任何正向结果，只能说明"参数调对了这批题"
- 不能说明"在未见题上会泛化"
- 可能是过拟合

---

### 问题 9：27.5% 基线暴露了系统性失败

**当前基线**：
- 14/51 = 27.5%（dev 题域，闭卷）
- 目标：30%（里程碑）→ 60%（最终）

**这意味着什么**？
- **73% 的题答错或答不出**
- 42/48 次调用走 novel 裸猜
- spurious 36/56

**为什么会这样**？因为整个架构建立在错误的假设上：
1. **假设**：污染物降解知识可以用反应数据库表示 → **错误**，需要化学规则和机制
2. **假设**：LLM 能从记忆中猜出合理产物 → **错误**，LLM 需要化学先验约束
3. **假设**：事后筛查能保证化学正确性 → **错误**，守恒检查能力不足
4. **假设**：完全匹配的 recorded 反应是唯一可信来源 → **错误**，排除了推演能力

---

### 问题 10：C2/C4 修改方案是在错误架构上打补丁

**C2/C4 试图做什么**？
- 给 LLM 更多信息（底物档案、候选上下文）
- 把推演候选注入 novel 任务

**这能解决根本问题吗**？不能。

**为什么**？
1. **知识表示没变**：仍然是"底物 → 产物"黑箱，缺少反应机制
2. **推理模式没变**：仍然让 LLM 从记忆中选，不是基于化学规则推理
3. **验证能力没变**：守恒检查仍是有限规则筛查，不是完整化学验证
4. **资格层没变**：推演候选注入 novel，但仍不是"合格候选"，只是"参考信息"
5. **路由决策没变**：仍然盲目决策，不看池里真正有什么

**C2/C4 的尴尬**：
- 试图通过"给 LLM 更多信息"绕过架构问题
- 但信息传递仍然断裂（五层漏斗）
- 在 dev 上可能有增益（因为针对 dev 设计）
- 在新题上效果存疑（过拟合风险）

**原提案承认**（173 行挑战清单）："C2 字段先验是否是'编目偏差'换皮？"——正确的担忧，但没有正视。

## 严厉的结论

**从污染物降解路径预测的目标出发，当前架构的根本问题是**：

### 你们不是在做降解路径预测，是在做检索+猜测系统

- **降解路径预测**：基于化学规则、酶机制、环境条件，推断可能的反应产物
- **你们在做**：检索相似反应 → LLM 猜常见代谢物 → 事后筛查

### 架构建立在七个错误假设上

1. ❌ 污染物降解知识 = 反应数据库
2. ❌ 只有完全匹配的 recorded 反应可信
3. ❌ 推演候选不如 recorded 候选，应排除在任务外
4. ❌ LLM 能从记忆中猜出化学合理的产物
5. ❌ 事后筛查能保证化学正确性
6. ❌ 有限规则筛查 = 完整化学验证
7. ❌ 在 dev 上调参的增益能泛化到新题

### 27.5% 基线是系统性失败的必然结果

- 42/48 次裸猜（因为资格层排除推演候选、路由层盲目决策）
- spurious 36/56（因为缺少化学约束、守恒检查能力不足）
- 94/162 题"看见没选对"（因为候选卡缺化学信息、模型无法推理）

### C2/C4 是打补丁，不是治本

- 不改知识表示、推理模式、验证能力
- 在 dev 上可能有增益（in-sample 调参）
- 在新题上效果存疑（泄漏 + 过拟合）

### 正确的架构应该是

**知识层**：
- 酶反应机制库（EC 分类 + 催化机制 + 底物特异性）
- 生物转化规则库（官能团转化 + 条件约束）
- 实测反应库（标注证据类型和可信度）

**推理层**：
- 基于官能团匹配生成候选（不是检索黑箱）
- 基于化学规则验证可行性（完整配平 + 氧化还原 + 立体化学）
- 基于证据类型评估可信度（实测 > 规则 > 类比 > 模板）

**LLM 角色**：
- 在化学合理的候选中排序
- 提供化学推理解释
- 处理边界情况（新官能团、特殊条件）

**验证体系**：
- 完整反应配平（所有参与物）
- 氧化还原对账（电子守恒、辅酶）
- 立体化学（手性、构象）
- 机制合理性（断键位置、中间体）

### 最后

**你们的"零训练优先、只动协议层"边界，与解决问题的实际需求矛盾**。

核心问题不在"LLM 怎么调用"，在"LLM 看到什么、基于什么做决策"。这需要改检索、资格、路由、验证等多个层面，不是协议层补丁能解决的。

**如果坚持只动协议层，27.5% → 30% 可能勉强够到（dev 调参），但 30% → 60% 是架构性鸿沟**，打补丁过不去。

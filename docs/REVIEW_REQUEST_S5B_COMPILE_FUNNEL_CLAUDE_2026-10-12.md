## 1. 系统背景（一段话）

我们做污染物酶催化降解预测：输入一个底物分子，输出"酶会把它变成什么产物"，按严格口径判分（产物与参考**严格身份相等**才算命中，不是沾边算对）。系统是"开卷考试"架构：先查三本参考库（EAWAG 环境库 4,454 条整反应记录 / RHEA 语料 37,100 条 / USPTO 松弛索引 188,725 条），把库里的反应**翻译成原子级编辑指令**（如"把 C–O 单键改成双键、两端各摘一个氢"），然后在底物分子上**真实执行**这些编辑得到产物分子，过审计（原子守恒/来源诚实），提交反应事件，最后零 LLM 判分。

关键架构哲学：**一切候选必须过公共链（编译→执行→审计）**——不许从库里直抄答案跳过执行（可审计性优先）。执行器（AtomTool）是一个原子操作解释器：change_bond_order / add_atom / form_bond / break_bond / remove_atom 等（协议版本 v43-editproto-2），执行后 sanitize 检查价态、产物 canonical 必须与声明的目标一致。

## 2. 问题：编译漏斗掐死了 96% 的候选

最新真实批次（chain12，298 题，判分 hit@1=92）的池层全量账：**5,498 个候选尝试 → 182 个编译成功（3.3%）→ 5,316 个拒绝（96.7%）**。执行链之后零损耗（去重/调度/执行/准入四环节合计 0 题损失），失分主战场是"120 题提交了事件但产物与参考不匹配"——其上游正是这个编译漏斗：**池子饿，而且池里的 182 个 spec 大多不是对的反应**。

### 2.2 关键背景：为什么对齐这么难

- **RHEA 全库 43,177 条记录的 atom_mapping 字段 0 条非空**——库里根本没存原子映射，我们的映射全靠结构相似性反推（推断映射 + 有限枚举）。这是 58.5% no_alignment 的结构性根源。
- 库记录的书写形态与题底物经常不一致：多组分记录（底物+共底物写成一条）、方向不一（LR/RL 双行各 18,550 条）、通配符行（8,502 条 * 行整体拒）。
- EAWAG 通道（唯一有完整整反应书写的库）的对齐失败率低得多——问题集中在 RHEA/corpus 通道和 analog 模板通道。

## 4. 硬约束（方案必须在内，越界=不可采纳）

1. 判分判据冻结（产物严格身份相等才计 hit@1）；判分零 LLM。
2. 公共链哲学：候选必须可执行、可审计——允许**换一种可执行的中间表示**（比如反应 SMILES/SMIRKS 解释器），不允许"从库直抄不执行"。
3. 参与物诚实：不许删共底物/辅因子换 strict（删了能涨分我们也不做）。
4. 编译/检索全程零模型调用（当前每题只允许 1 次模型调用、用在提案与排序上；编译期引入神经工具属于"离线预处理库"范畴可讨论，但需标注并过化学评审）。
5. 产物身份判定用 canonical SMILES（电荷归一+立体盲的 cn 口径）——身份口径冻结不动。

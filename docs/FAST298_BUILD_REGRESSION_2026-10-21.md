## 1. 方法与可信度（先说限制）

### 1.1 方法

FAST298 §4.3 建议用 `run_inputs/*.json` 的 `st_mtime_ns` 差值估算逐题墙钟。本轮照做：

- 对每个批根，按 manifest 的冻结注册序取 `run_inputs/<qid>.json` 的 `st_mtime_ns`；
- `delta_i = mtime_i − mtime_{i−1}`，归到第 i 题（包含该题的参考图构建、池检索/编译、
  JSON 序列化与写盘）；
- `startup = 第一个 run_input mtime − sacct Start`（含进程/资产初始化 + 第 1 题）；
- `finalization = sacct End − 最后一个 run_input mtime`。

### 1.2 可靠性验证（全部通过）

| 检查 | 结果 |
|---|---|
| 每个 HPC 批根：`startup + span + finalization` vs `sacct Elapsed` | **14/14 个批根误差 = 0 秒** |
| B3 GLM 实例 | 227 + 3,573 + 11 = **3,811 秒 = 01:03:31**（与 sacct 逐秒一致） |
| B3 两臂（不同节点、同工作）逐题差值 | Pearson **r = 0.9984**，平均绝对差 0.39 秒，最大差 1.0 秒 |
| mtime 粒度 | 该共享盘 `st_mtime_ns` 实际为 **1 秒粒度**（全部是 1e9 的整数倍）；B3 无 0 秒 delta |
| v44 根 mtime 归属 | 对应 a2/b2 重跑作业 `46383006/46383008`（早一轮被覆盖），Start/End 精确吻合 |

> **限制（必须一起读）**：逐题 delta 不是阶段计时器，它把「引擎展开 + 检索 + 编译 +
> 写盘」捆在一起；1 秒粒度对单题有 ±1 秒噪声，但 297 个 delta 的合计对 sacct 误差 0 秒，
> 所以**总量可信、单题只能看大数**。第 1 题的工作在 `startup` 里，无法与进程启动分开。

### 1.3 读数边界

- 只 stat 了 `run_inputs/*.json`（qid、mtime、size），**没有读 run_input 内容**；
- 只从 `batch_manifest.json` 取了诊断字段（候选计数、失败直方图、版本串等），
  **没有输出 substrate_smiles / n_gold_products**；
- 未读 `reference_graphs/`、题卷、金标、封存 run。

## 2. 现状账：B3 的 61–64 分钟花在哪

### 2.1 总账

|---|---:|---:|

两臂逐题曲线 r=0.9984，说明这 12 秒/题是**题目决定的稳定画像**，不是节点抖动。

### 2.2 逐题分布（B3 GLM，297 个 delta）

| 分位 | 秒 |
|---|---:|
| min | 5 |
| p25 | 7 |
| median | 8 |
| p75 | 10 |
| p90 | 25 |
| max | 56 |

**地板 5 秒/题**是第一个关键读数：即使候选很少、没有命中的题，也要 5 秒。本地同题地板
是 **1.64 秒**。地板差 ~3.36 秒 × 297 ≈ **16.6 分钟**（约 17 分钟），这是「每题固定
开销」的下界证据。

### 2.3 工作计数（B3 GLM，298 题合计）

| 量 | 读数 |
|---|---:|

作业申请 `--cpus-per-task=8`，但 build 是**单进程**，脚本还设了 `OMP_NUM_THREADS=1`；
这 61 分钟是**单核墙钟**。这不是回归原因，但解释了为什么加 CPU 不会自己变快（FAST298 P1-2）。

## 3. 分层特征与回归：慢题长什么样

把 297 个 delta 与 manifest 诊断字段做回归（B3 GLM）：

| 特征 | Pearson r | 斜率 | r² | 读法 |
|---|---:|---:|---:|---|
| `ncand`（候选行数） | +0.399 | +0.353 秒/候选 | 0.159 | 只解释 16% 方差；有影响但非主因 |
| 编译失败总数 | +0.465 | +0.454 秒/失败 | 0.216 | 失败尝试比成功编译更费时 |
| `corpus_diagnostics.n_matched_rows` | +0.518 | +0.032 秒/行 | 0.268 | 强相关，慢题集中在 corpus 命中多的底物 |
| `n_analog_compiled`（成功编译） | **−0.093** | 负 | 0.009 | 成功编译数与耗时**无关** |
| `pool_size` | −0.046 | 负 | 0.002 | 池大不等于慢 |
| run_input 字节数 | +0.080 | ~0 | 0.006 | 写盘体积不是主因 |

按候选数四分位：

| 候选数区间 | 平均 delta |
|---|---:|
| 0–7 | 8.64 秒 |
| 7–15 | 9.50 秒 |
| 15–26 | 10.23 秒 |
| 26–52 | **19.65 秒** |

按耗时三分位：

| 组 | 平均 delta | 候选数 | 失败数 | 成功编译 | 池槽 |
|---|---:|---:|---:|---:|---:|
| 快 1/3 | 6.4 秒 | 14.8 | 11.5 | 2.7 | 1.6 |
| 中 1/3 | 7.6 秒 | 18.0 | 14.2 | 3.1 | 1.9 |
| 慢 1/3 | **22.0 秒** | 20.7 | 17.6 | 2.6 | 1.9 |

**读法**：慢题确实候选更多、失败更多、corpus 命中更多，但成功编译数并不高。慢的尾部
是「复杂底物的检索/失败尝试多」，不是「编译成功次数多」。最慢的 5 题各约 54 秒，诊断
指纹完全相同（ncand=48、失败 46、corpus matched=1,392）；这正是 FAST298 §4.2 说的
重复底物形态（298 题只有 209 个不同底物），同一底物的池工作被逐 qid 重算。

> 重复底物重算是一条独立的优化线（FAST298 P1-3 估 ~30%，约 19 分钟），**不是**本轮
> 19→61 的回归原因；本轮只确认它会把慢底物成组放大。

**关于 remap 计数**：B3 报告里的 P2-face remap 计数（`remap_applied=242`、
`questions_remap=151`、`remap_add_atom_ge1=205`、`remap_add_atom_ge2=78` 等）是
`prepare` 阶段对 `run_inputs.plan.pools` 的只读统计，两臂逐字相同（`p2_face_measure.json`
同 SHA），**不参与 build**，因此不是 build 耗时的解释变量；本轮没有把它塞进回归。

## 4. 历史对照：19–22 分钟到底是谁的时间

### 4.1 同题、同 policy 家族的本地 vs HPC

| 项 | 本地 v44 A | HPC v44 A | 本地 v44 B | HPC v44 B |
|---|---:|---:|---:|---:|
| 批根 | `v44/reports/ppv1_s5b/v44_glm_298_a_g1` | `v44_glm_298_hpc2_a` | `v44/reports/ppv1_s5b/v44_glm_298_b_g1` | `v44_glm_298_hpc2_b` |
| policy | 5 | 6（T1a） | 6-rr1（T1a 前） | 6-rr1（T1a） |
| 墙钟 | **19:51** | **61:01** | **22:07** | **73:08** |
| 逐题均值 | **3.79 秒** | **11.57 秒** | **4.34 秒** | **13.96 秒** |
| 中位 / p90 | 2.14 / 6.58 秒 | 7 / 24 秒 | 2.84 / 7.43 秒 | 10 / 27 秒 |
| 地板（min） | 1.64 秒 | 5 秒 | 1.67 秒 | 5 秒 |

逐题配对（297 题）：HPC ≈ **1.67 × 本地 + 5.26 秒**，r=0.863，r²=0.746。
**不是纯 3× 乘法，而是「~1.7× 工作量缩放 + 每题 ~5 秒固定项」。**

### 4.2 关键反证：工作量计数几乎一样

| 计数 | 本地 v44 A | HPC v44 A |
|---|---:|---:|
| recorded lookup 行 | 322 | **322** |
| corpus matched 行 | 9,712 | **9,712** |
| corpus 共底物候选 | 1,323 | **1,323** |
| 编译失败 | 5,336 | 5,316 |
| analog 成功编译 | 77 | 94 |
| **编译尝试合计（失败+成功）** | **5,413** | **5,410** |
| 池槽 | 165 | 182 |
| **逐题耗时** | **3.79 秒** | **11.57 秒** |

检索行数逐项完全相同，编译尝试合计只差 3 次（0.06%），但耗时差 **3.05×**。
两批 298/298 题的 `corpus_v1_sha256` 也同为 `186a1dad…`，说明检索资产同源。
这排除了「HPC 上题目/资产/检索面不同」的解释；也说明 T1a 候选诊断行（绝大多数是
纯 dict 记录，只有成功编译的候选才算签名——v44 A 全批仅 94 个 analog 成功编译）
不可能贡献 7.8 秒/题。

### 4.3 必须排除的假证据

| 看似 20 分钟的记录 | 真相 |
|---|---|
| HPC `46370575` / `46370578`：20:33 / 22:34，**FAILED** | RDKit 2024.03.2 在 `Chem.MolFragmentToSmiles` 抛 `Invariant Violation` 崩溃；**不是完成的 build**，不能当 20 分钟基线 |
| HPC `46342037`：3:14，`s5b_298_hpc` | 该批根 298 条 `pool_size=0`、候选 0（日志有 `No module named 'numpy'`）；**空池冒烟，不是全量 build** |
| `chain13q/d` 的 56:40 | `CANCELLED+`（重复提交被取消），不是完成时间 |

**目前 HPC sacct 里没有任何一次「完成的」19–22 分钟全量 build。** 19–22 分钟只出现在
本地 v44 仓的两次 build（以及两次 HPC 崩溃尝试的巧合时长）。

## 6. 三档归因

### 6.1 已证（同题/同字段对照）

1. **19–22 分钟不是 HPC 数据**：来自本地 v44 仓两次 build（`HANDOFF...:46-47` 原文
   「本地 A/B build」）。HPC 完成的同题 build 从 2026-10-12 起就是 61–73 分钟。
2. **不是 policy-9 / compiler-5/6 / F5 / corpus 门的代码回归**：61+ 分钟档在 policy-6/7
   就存在；policy-6→9 + compiler-5→6 全部演进只 **+0.46 秒/题**；逐题曲线 r=0.97–0.98。
3. **不是「编译次数变多」**：本地/HPC 检索行数完全相同（322 / 9,712），编译失败数差 0.4%；
   policy-7→9 成功编译 6.5×，时间 +0.08 秒/题；候选数只解释 16% 方差。
4. **方法可信**：mtime 合计对 sacct 误差 0 秒；两臂 r=0.9984；1 秒粒度已披露。

### 6.2 推断（时间相关/回归拆账，未逐阶段计时）

1. HPC 逐题时间 ≈ **1.67 × 本地工作量 + 5.26 秒固定项**；固定项约占 12 秒均值的 44%。
2. 固定项里可测的一段：`AnalogSourceResolver` 每题构造都会调 `verify_repo_manifest`，
   对 167 MB 资产逐文件重算 SHA256——HPC 热缓存 **0.58 秒/题**（冷 1.19 秒），本地热
   0.06 秒/题；全程差约 **155 秒（2.6 分钟）**。
3. 近似的总量分解（43.7 分钟差）：启动差 ~2.9 分钟 + 每题地板差 ~16.6 分钟 +
   工作量缩放差 ~24.2 分钟。**这是近似拆账，不是精确阶段计时。**
4. 慢题尾部由复杂底物的 corpus 命中/失败尝试驱动（`n_matched_rows` r=0.518，
   编译失败 r=0.465），且重复底物会成组重算（5 题同指纹各 ~54 秒）。

### 6.3 unknown（不要当成已解决）

1. **5.26 秒/题固定项的内部构成**：`engine.expand_raw`、analog 编译、共享盘写盘、
   Python/RDKit 构建差异各占多少——没有阶段计时器，无法拆。
2. **HPC 节点 CPU 型号 vs 本地 Mac 单核倍率**：未做受控微基准；只知道 `wzhcnormal`
   节点 32 核（部分 i 节点 64 核），build 单核运行。本地/HPC 的 Python/RDKit 构建、
   `vendor/v3_engine` 编译优化是否逐字同也未比 SHA——这些都归在「环境」未知里。
3. **同底物缓存的真实收益**：FAST298 估 ~30%（约 19 分钟）是上限；参考图/写盘仍按 qid
   发生，实际会低于上限。
4. **`v44 A` 本地 policy-5 vs HPC policy-6 的 17 个池槽差异**：来自编译结果的小差异，
   不影响 3× 结论，但未逐题归因。

## 7. 下一步最小验证实验（只测，不改）

按性价比排序；前两项就能把 5.26 秒固定项劈开。

1. **阶段计时（一刀）**：在一次性隔离副本里，对 5 个最快 + 5 个最慢 qid 加
   `perf_counter`：① `build_reference_graph` ② `engine.expand_raw`
   ③ `find_corpus_recorded_exact` ④ `AnalogSourceResolver(...)`（含 manifest verify）
   ⑤ `templates_similar_to` ⑥ analog 编译循环 ⑦ 两个 JSON 写盘。同一份代码在 HPC
   计算节点和本地各跑一次。**这是唯一能把「引擎/编译/IO/固定项」拆开的实验。**
2. **CPU 微基准（零批根）**：20 个合成分子，做 RDKit parse + 子结构匹配 + 反应枚举，
   在 HPC 节点与本地各跑 30 秒。若 HPC/本地 ≈ 1.7，则斜率主要是 CPU；若 ≈1.0，
   则固定项主要是共享盘/环境。
3. **manifest verify 缓存对照**：同一进程内 298 次 `verify_repo_manifest` vs 1 次。
   已测得 0.58 秒/题 → 298 次约 173 秒；一次验证可省约 2.9 分钟（仍属固定项，不是主因）。
4. **同底物缓存 A/B（10 个重复底物 qid）**：只复用池/编译结果，参考图与 run_input 仍
   按 qid 产出；量实际节省，验证 FAST298 P1-3 的 30% 上限。
5. **不要先做**：在阶段计时之前上 build 多进程。现在只知道总账，8 路并行会把固定项
   和慢题尾部一起放大，无法判断收益来源。

# probe-before-build — 零 LLM 探针先行

> 状态：L1 已完成（2026-10-26）。检查脚本已实现（`scripts/bible_checks/check_probe_before_build.py`）。

## 1. 一句话规则

任何修复/新功能立项前，先用零 LLM 探针实测召回与误拒，数字过门才写代码。

## 2. 为什么

不跑探针就立项，最便宜的结局是白写代码，最贵的结局是拿「代理数字」
当收益写进汇报——仓里已经有两轮（L3、L1 mask）是探针一跑就把
整个方案前提打成空集的。探针是零模型零网络成本的，它花的是半天，
省的是一轮付费批。

## 3. 细则

1. **先证「新增面非空」，再谈修法**：任何「给 X 类候选补 Y」的方案，
   第一步是对全量产物跑只读投影，数出真实命中多少行/多少题；为零就
   结项，不为凑方案放宽判据。
2. **代理口径必须换成实施口径重测**：探针的筛选口径（如「方向无关
   并集」）比实施判据（如「反应物侧额外组分」）宽时，宽口径数字只能
   当上界线索，不能当收益估计。
3. **「可能是空集」的推断必须落成探针**：读源码推出来的疑点写进
   方案时标「待探针」，禁止在未跑面前把它写成「已证实为空」或反过来
   「已证可行」。
4. **误拒率这类带判断的实测要带一致性门**：抽样 → 判读 → 二读一致
   性复算 → 终审；门不过回炉，不直接消费第一轮读数。
5. **探针产物 ≠ 成绩 ≠ 预注册**：探针报告标题与结论都要带
   「探针≠预注册≠成绩」标签；探针数字进预算/收益语境前必须降级为
   「上界/待证」。

## 4. 反例

反例：L3「给普通门候选补声明」代理面 55 题，精确判据实测 0 行/0 题
（`docs/C_COSUB_SUPPLY_REDESIGN_PREREG_2026-10-15.md:2`（勘误头），
结项读数 `docs/CHAIN13_HIT50_DIAGNOSIS_GPT_2026-10-15.md:90`）
发生什么 → 旧方案按宽口径（方向无关供体∪产物并集，水在产物侧也被
计入）估出 55 题/60 行/「10 题新增潜力」；Phase A 探针改用精确判据
（反应物侧额外组分）重测，L3 目标集 = 0 行/0 题，锁3「普通门 spec
无声明面」经实测关闭。
→ 后果：L3 线结项，旧收益估计全部撤销；后续任何引用 B 面数字的
方案须先重跑面数实测证伪（勘误头原话）。
→ 正确做法：立项前用实施判据跑面数探针；宽口径只当筛选线索。

反例：模拟解锁 13 题预期兑现，实际 0/13
（`docs/CHAIN13_HIT50_DIAGNOSIS_GPT_2026-10-15.md:46`）
发生什么 → chain13 预期中的模拟 13 题实际兑现 0/13，并非 5/13；
该集合救援计数与声明计数均为零，297 个候选中 289 编译拒绝——
「供给资格与编译没有接通」。
→ 后果：实际救回的 5 题是另一个集合，不能拿来充当模拟面的兑现率；
C 供给机制闭环跑通但没接到目标题上。
→ 正确做法：机制装好不等于接到目标面；上线前用探针验证
「目标题确实走过新机制」。

反例：「旧口径无候选」是误名——41 题旧口径都有 3–16 条候选
（`docs/T_H_TOP3_LEVERS_REPORT_2026-10-21.md:74`）
发生什么 → 杠杆 2 早期口径把 41 题记为「旧口径无候选」，实测
`old.n_candidates=0` 为 0/41，其中 13 题还有 `width_capped_products`。
→ 后果：58 题次的死因改写——不是「remap 没召回」，而是「有候选、
编译后身份/对齐/覆盖没匹配上」，修复方向完全不同。
→ 正确做法：「无候选」「无匹配」「被拒」三个词对应三种不同的
探针读数，动笔前先跑清楚是哪一种。

反例：L1 新资格 mask 被推断「可能是空集」，未跑探针前不得当已证
（`docs/CHAIN13_HIT50_DIAGNOSIS_GPT_2026-10-15.md:104`）
发生什么 → 上轮方案的资格条件 `analog & front_gate_rejected &
!current_C_eligible`，读源码后发现现行 C 可能已覆盖同类候选，即
该「新增」mask 可能是空集；本会话未执行面数探针，报告如实写
「不能把'可能空'写成已实测为零，也不能继续把它当已证可行方案」。
→ 正确做法：把「可能空」降级为待证假设，探针排进下一轮第一步。

## 5. 检查清单

开工前：
- [ ] 方案前提（目标面非空、误拒不成立、机制可达）各自对应哪个探针？
- [ ] 探针是零 LLM 零网络吗？读的是封存产物还是活批根？
- [ ] 探针口径 = 实施判据口径吗？不一致时宽多少、方向是什么？

发车前（探针过门才立项）：
- [ ] 新增面行数/题数 > 0 且有逐行出处？
- [ ] 误拒率实测过了预注册门（含一致性二读）？
- [ ] 暴露面风险（新增候选挤掉现有 strict 的题数）量化了？

交付前：
- [ ] 探针数字带「探针≠预注册≠成绩」标签？
- [ ] 旧方案被证伪时，旧收益估计撤销声明落盘了？
- [ ] 探针产物与脚本进 evidence 目录并带 SHA256SUMS？

## 6. 机器检查

脚本：`scripts/bible_checks/check_probe_before_build.py`（已实现，
契约见 `docs/BIBLE/_CONTRACT.md` §五）。

预期行为：给定方案 md（`--files`），检查其中「新增/解锁/召回」类
数字是否附带探针出处（`review_evidence/` 路径或 probe 报告指针）与
「探针≠预注册≠成绩」标签；无出处的新增面数字 → fail。手工阶段
用第 5 节清单，重点盯第 3 条（待证假设不冒充已证）。

## 7. 模板（探针立项头）

```markdown
# <X> 面数探针（<日期>）
- 性质：零 LLM 零网络只读探针；探针≠预注册≠成绩。
- 输入：<封存批根/隔离副本>，未读金标正文。
- 判据口径（与实施一致）：<精确定义>；宽口径对照：<定义+差多少>。
- 出数：新增 <N> 行 / <M> 题（逐行清单见 evidence）；误拒率 <p%>
  （Wilson95 [<a>,<b>]，二读一致性 <r>%、κ=<k>）。
- 门：<阈值>；过/不过 → 下一步：<立项 / 结项并撤销旧估计>。
```

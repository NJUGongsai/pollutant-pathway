## 2. novel 死引用：机制与量级

### 2.1 现象
模型输出形如：
```json
{"proposals": [{"hypothesis_id": "novel-1", "coproducts": []}, ...],
 "rank_hypotheses": ["novel-1","novel-2","hyp_xxx",...]}
```
但**从不提供** `novel_proposals: [{hypothesis_id, reaction_spec: {edits, donor, alignment, expectation}}]`。

代码路径（`runflow.py:930`）：只有 `model_note["novel_proposals"]` 才会被 prepare 成候选；
`proposals` 里的 `novel-N` 仅作为 rank 的 key，找不到对应 prepared entry ⇒ 静默 fallback 到池声明序。

### 2.2 分布

| 分组 | 题数 | 状态分布 | 池宽 |
|---|---:|---|---|
| rank0 = novel 且池宽 0 | 60 | strict 25 / partial 12 / unmatched 23 | 全部 0 |
| rank0 = novel 且池宽 ≥1 | 41 | strict 14 / partial 4 / **unmatched 23** | 1:13 / 2:12 / 3:9 / 4:6 / 8:1 |

- 前 60 题：空池，模型没得选，提 novel 属合理；无 spec 使其必然无效（本来也无池可提交）。
- 后 41 题：**池里有 1–8 个候选，模型仍首选空 novel 引用** ⇒ 27 题失分。这是可修复面。

### 2.3 为什么这是"可修复"而不是"模型能力不足"
模型没有给出"我认为池候选都不好"的显式理由，也没有给出 novel 的可执行内容；
它只是产出了一个格式上不完整的引用。系统对此**零反馈**（不触发格式反馈轮），模型无从纠正。

## 3. 排序干预

41 题（rank0=novel 且池非空）里：

| 情形 | 题数 |
|---|---:|
| events[0] == 模型 rank 里第一个 hyp | 9 |
| 该 hyp 被提交但不是第一位 | **32** |
| 该 hyp 未进 payload | 0 |

32/41 = 78% 的题，模型对池候选的偏好被其他候选挤后。
可能来源：去重折叠（同净反应签名合并）、fallback 序、位次策略（W3 rank-policy-1）。
**未定位到具体原因**——需要逐题核 effective_rank 与去重记录（下一步）。

## 4. 修复候选（全部在白名单内：工程层，不改判据）

| # | 修复 | 影响面 | 风险 |

| R1 | **检测死引用并触发格式反馈**：`proposals`/`rank` 引用 `novel-N` 但 `novel_proposals` 缺 spec ⇒ 发格式反馈要求补 spec 或改选池候选（复用现有 feedback 通道） | 41 题（27 失分） | 多一轮模型调用（token ↑）；须防反馈循环 |

## 6. 证明范围

**能证明**：在上述 298 题与代码锚下，模型引用层与提交层之间存在 14% 的低采纳率，且 novel 死引用影响 101 题（41 题池非空）。

**不能证明**：① 修复后能提升多少 hit@1（需付费重跑）；② 模型提 novel 是否出于"池候选质量差"的正确判断（需读模型理由，本批未记录理由字段）；③ 其它批/其它模型的同类比例。

**未做**：32 题排序干预的逐题定位（R3）、空池 60 题的 fallback 质量评估。

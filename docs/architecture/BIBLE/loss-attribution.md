# loss-attribution — 失分桶闭合、逐题配对 diff

> 状态：L1 已完成（2026-10-26）。检查脚本已实现（`scripts/bible_checks/check_loss_attribution.py`）。

## 1. 一句话规则

失分必须拆到互斥桶且桶合计等于分母，逐题配对看改善/退化换手，拒绝条数不换算丢分。

## 2. 为什么

只看总分差（+2、−5）什么都学不到，而且极易被「拒因条数大 = 这就是
损失来源」这种直觉带偏——仓里最大的一次口径事故（992 当 F3）就是
从「数字大所以重要」开始的。闭合的桶 + 逐题配对 diff 才能回答
「丢的题丢在哪、赚的题赚在哪、两拨是不是同一批题」。

## 3. 细则

1. **桶要互斥且闭合**：任何分箱必须满足「桶合计 = 分母」（如 5319 =
   531+4311+472+5；298 = 126+53+119）；报桶之前先做闭合验算。
2. **逐题配对 diff，不看净差讲故事**：跨批比较报「改善 g / 退化 l /
   持平」三联数（如 18 改善、16 退化、264 持平）；「没有净回收 N 题
   这种读法」——strict 涨 7 里可能同时有 31 题改善和 15 题退化。
3. **换手分析**：旧命中掉出去的题（loss）优先于新命中（gain）检查；
   换手率高（如 34/298 = 11.4%）说明两批差异远比净差大。
4. **拒因条数 ≠ 丢分**：拒因是候选行级计数，不能换算成题级损失
   （F5 拒 864 条覆盖 194 题，其中 58 题仍 hit@1）；「题次 ≠ 丢分」
   同理（身份门拒 13 题次，被拒 spec 是否含正确候选 unknown）。
5. **关联不写成因果**：remap-only 面 5.88% 命中 vs 非 remap 对照
   36.05% 是同批描述性关联，没有同题 A/B 就不能写「remap 导致丢分」。
6. **测量修正与工程回收分账**：判据口径变化带来的分数变化（v1→v2
   的 +5）单独记账，不与工程修复效应（净 +2）混在一句结论里。

## 4. 反例

反例：strict +7 被误读为「净回收 7 题」——实际 31 题改善、15 题退化
（`docs/T_H_RESULT_2026-10-20.md:21`，换手表 `:255`–`:257`）
发生什么 → T-H strict 从 119 涨到 126，粗看是 +7 回收；逐题配对
是 31 题改善、15 题退化（46 题换手），hit@1 层面更是 18 进 16 出。
→ 后果：报告明写「没有'净回收 7 题'这种读法」；若按 +7 宣称修复
成功，就把同量级的退化藏掉了。
→ 正确做法：任何跨批差值必须附 g/l/持平三联数与换手率。

反例：992 与 864 重叠 814，「864+992」会把 814 数两遍
（`docs/T_H_P3_O0_METRIC_RECONCILIATION_2026-10-23.md:68`，更正表 `:18`）
发生什么 → `analog_pregate_skipped`（992）是横跨三个分支的诊断
计数器，与 F5 reject（864）重叠 814；早期文档把 992 当「F3 条数」
引用，并出现了与 864 相加的写法。
→ 后果：P3 O0 专门做了一轮口径对账，把 992 定义为 counter 单位、
规定「禁止与任何候选行数相加」；1585 的唯一互斥可加拆分是
864+543+178。
→ 正确做法：相加之前先验互斥；计数器（counter）永远不与行数/题数
混算。

反例：硬编码「全部 post-compile」被 Codex 复核推翻
（`docs/T_H_TOP3_LEVERS_CODEX_REVIEW_2026-10-21.md:46`）
发生什么 → 杠杆 2 审计脚本第 209 行把每个非 hit 题次直接赋值为
`post_compile_match_coverage`，没有沿具体候选追到选择/执行/提交/
匹配，于是得出「57/58 全死在编译后」。
→ 后果：该「独立诊断结果」被判为赋值规则而非定位证据；归因结论
降级为「已见编译候选、根因未定」。
→ 正确做法：死因字段必须是逐题追踪出来的，不允许脚本按频数或
优先级直接赋值后冒充诊断。

反例：保持格迁移账不闭合——115/110 是错的，闭合值 107/111
（`docs/CHAIN13_HIT50_DIAGNOSIS_GPT_2026-10-15.md:185`）
发生什么 → chain13 归因报告的 v1 保持格写 S→S=115、U→U=110，
与同文迁移表矛盾；用公开聚合数闭合：130−10−13=107、125−5−9=111。
→ 后果：按「错误行登记、原文件不回写」处理，闭合值成为引用口径。
→ 正确做法：迁移矩阵每行每列都要能用初值±迁移数闭合验算。

## 5. 检查清单

开工前：
- [ ] 桶定义互斥吗？分母选的是题/候选行/spec/事件中的哪一个，标了吗？
- [ ] 配对 diff 的两批口径一致（同 v1 或同 v2）？

发车前：
- [ ] 预注册里写死了回查时的分桶方式与对照基准（如「以 chain13 桶为锚」）？
- [ ] 候选级归因需要的数据（逐事件金标匹配明细）这一批拉不拉？不拉就预写 unknown。

交付前：
- [ ] 每张桶表做了「合计=分母」闭合验算？
- [ ] 差值结论附 g/l/持平与换手率？
- [ ] 没有用拒因条数、代理面、上限池（如 +37）直接当丢分或收益？
- [ ] 测量修正与工程回收分账了？

## 6. 机器检查

脚本：`scripts/bible_checks/check_loss_attribution.py`（已实现，
契约见 `docs/BIBLE/_CONTRACT.md` §五）。

预期行为：给定含分桶表的 md，抽取形如 `A = B + C + …` 的闭合等式与
桶表数字做算术验算；发现「净 ±N」结论句而无配套 g/l 数 → fail；
发现已知计数器名（如 `analog_pregate_skipped`/992）出现在加法里 →
fail。手工阶段用第 5 节清单，重点第 1、2 条。

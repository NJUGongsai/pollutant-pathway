# stop-loss-gate — 未达线强制回查、不虚宣有效

> 状态：L1 已完成（2026-10-26）。检查脚本已实现（`scripts/bible_checks/check_stop_loss_gate.py`）。

## 1. 一句话规则

结果未达预注册线就触发强制回查；净增益不超过噪声，一律不得宣称修复有效。

## 2. 为什么

止损门防的是两种自我欺骗：一是没到线就「总结经验宣布部分成功」，
二是把 ±2 题的噪声波动说成修复兑现。仓里的实践是把两者都程序化：
未达线自动进逐桶回查，回查结论由算术给出（净 +2 vs 噪声同量级），
不由 wishful thinking 给出。

## 3. 细则

1. **线与动作绑死**：预注册写「未达 X 则强制回查」（如 <32%/<96 题），
   触发时回查是义务不是选项；回查结论必须回写进结果报告结论节。
2. **宣称有效须过双条件**：净增益过推进线（如同批对照净增 ≥5 题）
   且覆盖/分族无净退化（如 strict 较对照不降）；只满足其一不算。
3. **上限池不当收益**：「37 题若全部排第一是 +37」是数学上限，实际
   兑现 unknown；任何「毛空间」数字进结论前必须降级为池/上限标签。
4. **门停 = 按规则执行**：阶段门触发停批（如 smoke10 门）是预注册
   行为，处置走选项表（新批/回炉/上报），不指责脚本误杀、不就地放宽。
5. **外部评审可以否决「已闭合」**：评审（Codex/代审）认定证据不足时，
   「三项成因全部闭合」「44 题已证可修」一类结论必须降级回收。
6. **止损止损在花大钱之前**：`g≤l` 或净增 ≤0 直接关闭该假设/路线，
   不「再试一轮看看」；确认策略事前固定，不连跑到正为止。

## 4. 反例

反例：T-H r2 未达 32% 回查线 → 强制回查 → 净 +2 不宣称有效
（触发 `docs/T_H_RESULT_2026-10-20.md:18`，回查结论 `:284`–`:286`）
发生什么 → v1 84、v2 89 均低于 96 题（32%），强制回查成立；回查
按 chain13 同口径逐桶配对：净 +2 题（87→89），18 改善/16 退化，
改善桶（partial +4、unmatched +6）与退化桶（原 strict −8）互相抵消。
→ 后果：报告结论是「净增益与批次噪声同量级，不能宣称修复包带来
了 35–40% 线所需的提升」——而不是「+2 也是正收益」。
→ 正确做法：触发即回查、回查即出算术结论、结论照抄进 headline。

反例：+37 是数学上限不是收益，chain15 不立项
（`docs/T_H_TOP3_LEVERS_REPORT_2026-10-21.md:50`，决定 `:119`）
发生什么 → 杠杆 1 找到 37 题 strict 非首位，看似「+37 的空间」；
逐题归因后 37/37 是模型显式排序，执行层可修对象 0/37。
→ 后果：报告给 +37 标「池/上限」，明确「实际能兑现多少 unknown」，
chain15 暂不立项，只输出提示词变量清单。
→ 正确做法：毛空间数字永远带「池/上限」标签；立项决策看的是
可修对象数，不是空间大小。

反例：评审否决「成因全部闭合」——赋值规则不等于诊断证据
（`docs/T_H_TOP3_LEVERS_CODEX_REVIEW_2026-10-21.md:10`，收口 `:106`）
发生什么 → 三杠杆结论稿宣布「三项成因全部闭合、44 题已证可修」；
Codex 复核认定三处关键决策均超证据（排名来源未核、post-compile
是硬编码、可修是分类器赋值）。
→ 后果：总裁定「需回修，当前不能据此宣布」；「当前对 hit@1 的结论：
三份表尚未给出一项已证能净提分的修复」。
→ 正确做法：宣称闭合前先过独立评审；被否后按最小回修清单收窄
结论而不是辩护原文。

反例：推进线事前写死，净增不足就止损
（`docs/T_H_TOP3_LEVERS_CONCLUSIONS_FOR_REVIEW_2026-10-21.md:150`、`:152`）
发生什么 → 实验设计草案把推进条件写死：B−O 净增 ≥5 题（1.68pp）
且 strict 不降才进确认轮；净增 1–4 题只记小信号不默认续跑；
净增 ≤0 终止该版本提分路线。
→ 正确做法：确认策略事前固定，「不连跑到正为止」；历史 89 只当
背景参照，不充当同批对照。

## 5. 检查清单

开工前：
- [ ] 本轮目标线与回查线从预注册原文抄录了吗？
- [ ] 「宣称有效」的条件（净增阈值 + 无净退化）写死了吗？

发车前：
- [ ] 阶段门（smoke/full）阈值与触发后的处置选项表已进预注册？
- [ ] 臂间连停的代价评估过（见 `batch-discipline`）？

交付前：
- [ ] 未达线 → 回查执行且结论回写 headline？
- [ ] 所有「空间/池/上限」数字带标签，未冒充收益？
- [ ] 净增益是否对照噪声量级（区间/换手）说明过？
- [ ] 评审否决点是否已按最小回修收口，未继续宣称原结论？

## 6. 机器检查

脚本：`scripts/bible_checks/check_stop_loss_gate.py`（已实现，
契约见 `docs/BIBLE/_CONTRACT.md` §五）。

预期行为：给定结果报告 md，若检出「有效/兑现/成功回收/修复带来」
类宣称句，则要求同文存在：①预注册线原文引用与实测值对照；
②净增益与噪声对照（区间或换手数）；③同批对照臂或明确降级声明。
缺任一 → fail。手工阶段先核对第 5 节前三条。

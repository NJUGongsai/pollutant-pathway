# review-loop — 多 AI 评审环与代审标注

> 状态：L1 已完成（2026-10-26）。检查脚本已实现（`scripts/bible_checks/check_review_loop.py`）。

## 1. 一句话规则

交付必过「正链复审 + 化学评审」双通道；代审如实标注身份，意见采信到互证为止。

## 2. 为什么

实施者自查自己写的代码，漏洞率天然高——chain14 发车评审一轮就抓出
4 项 P1（每题预算漏记、重放挡死、恢复参数错、冻结副本静默变 B），
任何一项上了付费批都是真金白银的损失。评审环是质量上的「同批对照」：
独立通道、独立执行、结论与程序证据互证后才采信。

## 3. 细则

1. **双通道各管一摊**：程序/存储/身份事实归 Codex 正链复审；化学判据
   归 mimo（或同级）化学评审；两通道结论都只采信到「与源码及程序
   证据互证」的程度，不做独立性背书。
2. **代审必须逐字标注 provenance**：Codex 无额度时由 qwen3.8max /
   ZCode 子代理代审，头部写明「X 代 Codex 复审/代决……不冒充 CC
   本人，不替代正链 Codex 的最终复核权」，并列 CC 后置复核项。
3. **正链额度耗尽走既定顺序**：撞额度默认切备用通道（通道 C 等），
   不干等重置；备用通道报告 provenance 注明通道，放行/冻结类重要
   轮次在正链恢复后可复核确认。
4. **评审请求自包含**：边界头（只读/无执行权限/禁金标/行号漂移警示）
   + 零金标内容 + 对外数字带题域标签 + 定好回复格式；代码行号引用
   要注明核验时 HEAD。
5. **评审发现的「已过」冲突必须登记**：草稿写「R4 已过」而实际是
   `PASS_WITH_CONDITIONS` 这类冲突，纠正后原稿标注待改、不改写历史件。
6. **fork 链保持上下文连续**：Codex 复审用链式 fork（每轮记
   `session id:`），必须在仓库根目录发起；主对话被写锁时不用 resume
   硬敲。

## 4. 反例

反例：代审不冒充——provenance 逐字落头部
（`docs/T_I_C8_STOP_QWEN_DECISION_2026-10-21.md:3`–`:5`，同型
`docs/T_P2_V2_CHEM_REVIEW_ROUND3_2026-10-21.md:3`–`:4`）
发生什么 → Codex 无额度，C8 停点裁决由 qwen3.8max 代 Codex 执行。
→ 后果（正面处置）：报告头部逐字写「qwen3.8max 代 Codex 复审/代决，
按 CC 指示……不冒充 CC 本人，不替代正链 Codex 的最终复核权——
CC 后置复核项见 §7」；P2 arm_a_definition 的代决同样逐字登记
`qwen3.8max 代 Codex 代 CC 确认……不伪填 CC`
（`docs/HANDOFF_MAIN_TO_P2_2026-10-21.md:52`）。
→ 正确做法：代审件头部三要素：代审者身份、授权链、后置复核项。

反例：评审环抓住 4 项 P1，发车被否
（`docs/CHAIN14_LAUNCH_CODEX_REVIEW_2026-10-16.md:3`，逐项 `:7`–`:10`）
发生什么 → chain14 发车物整体代审：反馈首发登记成 scripted 导致
每题 4 次真实发送只预约 3 次预算；重试成功后崩溃重放被旧 failed 记录
挡死；worker 恢复传了不存在的参数把合法中断写成失败终态；冻结 A 的
副本丢失后 worker 静默按 B 跑、批报告仍报 off。
→ 后果：总裁定「不放行（回修 P1-1～P1-4 后同范围复核）」。
→ 正确做法：发车门是评审环的产物门——评审不放行就不发车，
回修后同范围复核，不绕审。

反例：设计稿写「R4 已过」与实际 `PASS_WITH_CONDITIONS` 冲突
（`docs/HANDOFF_MAIN_TO_P2_2026-10-21.md:79`）
发生什么 → P1-B 预注册确认发现设计稿 line 378 写「R4 已过」，
而 R4 全文是 PASS_WITH_CONDITIONS（C1–C4 未闭合）。
→ 后果：CC 纠正并入：「不写'已过'」，冲突处登记待改（本窗口不改，
不回写历史稿），并新增 M8/M9 两条评审要求。
→ 正确做法：条件通过（PASS_WITH_CONDITIONS）永远不得简写成
「已过」；发现的冲突登记到差异清单，等下一轮修订消化。

反例：评审推翻「全部闭合」——互证原则的实况
（`docs/T_H_TOP3_LEVERS_CODEX_REVIEW_2026-10-21.md:10`）
发生什么 → 三杠杆结论稿被 Codex 复核认定三处关键结论超证据
（见 `stop-loss-gate` 反例三）。
→ 后果：按「需回修」处理，最小回修清单 R1–R4 收口；实施方对
复核中自己错的点（如 58 题次重叠数 6→7）也直接采纳更正。
→ 正确做法：评审意见与源码/程序证据互证后，谁错改谁，不分
评审方/实施方。

## 5. 检查清单

开工前：
- [ ] 本轮交付走哪条评审链（正链 Codex / 通道 C 备用 / 代审）？额度状态查了吗？
- [ ] 化学判据类变更是不是也该出 mimo 评审请求（三触发点）？

发车/送审前：
- [ ] 评审请求自包含：边界头、零金标、题域标签、回复格式？
- [ ] 代码行号引用注明核验 HEAD？
- [ ] fork 链父 session id 与发起 cwd（仓库根）确认？

交付前：
- [ ] 代审件头部 provenance 三要素齐（身份/授权链/后置复核项）？
- [ ] 评审结论未越过互证限度（执行类声明标「待执行验证」）？
- [ ] P1/条件项逐条有最小回修或登记，没有「下次再说」？
- [ ] 回复原文落盘 docs/、证据进 review_evidence/ 且带 SHA256SUMS？

## 6. 机器检查

脚本：`scripts/bible_checks/check_review_loop.py`（已实现，
契约见 `docs/BIBLE/_CONTRACT.md` §五）。

预期行为：给定评审类 md（`--files`），检查：①含「代审/代 Codex/
备用通道」字样的文件头部是否有 provenance 块（代审者身份 + 不冒充
声明 + 后置复核项）；②「已过/放行」类结论是否有对应评审件指针；
③请求类文件是否含禁金标与只读边界声明。缺任一 → fail。手工阶段
用第 5 节清单。

## 7. 模板（代审件头部）

```markdown
> **provenance：<模型/代理> 代 Codex 复审/代决，按 CC <日期> 指示**
>（Codex 无额度/<原因>；不冒充 CC 本人，不替代正链 Codex 的最终
> 复核权——CC 后置复核项见 §<n>）。
> **题域标签：[<域>]。** 本文件是 <裁决/复审>，不含科学成绩。
> 审阅环境：<隔离树/主仓只读>，实际 HEAD `<hash>`。
> 本轮未：<执行/付费/金标/env/key 触碰清单>。新增文件仅本报告。
```

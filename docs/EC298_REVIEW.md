# EC298 首跑结果 Review

**审查对象**：`docs/EC298_REPORT.md` 与远端 `runs/ec298_v43r1/` 首跑产物  
**审查范围**：结果口径、评分实现、候选池诊断、空答来源与验收状态  
**结论**：**当前报告不通过结果验收。** 首跑数据可保留；主对比和候选池归因须在报告前修正。本文只记录 review，不修改首跑答卷、评分结果或代码。

## 摘要

298 个 qid 均有唯一答卷，题卷隔离与运行完整性未发现明显问题。当前报告的主要结论仍不能采信：引擎臂的评分直接比较了未做 `cn` 归一化的 `product_identity` 与已经归一化的金标，明显压低了引擎成绩；此外，“完整候选池”三档实际只基于 Top-10。agent 侧的 51 条空答也有明确原因，其中 23 条是 AtomTool 编辑检查拒绝、28 条是模型弃答。

| 优先级 | 发现 | 影响 |
|---|---|---|
| P1 | 引擎臂身份没有按 `cn` 归一化 | 报告的 agent 对引擎 hit@K 差值错误 |
| P1 | “完整候选池”实际只保存 Top-10 | `gold_in_pool_beyond_top10=0` 与“池内无金标”结论不成立 |
| P1 | AtomTool 将已有单键上的键级变化拒绝为重复成键 | 23 条模型预测被拒，直接形成空答 |
| P2 | 多组分预测字符串的计分单位未定义 | 18 条预测含点号；组件级重算会改变命中数 |
| P2 | 报告缺少逐题失败归因和预测宽度诊断 | 很难解释 51 条空答及 hit@3/5 表现 |
| 验收项 | 40 次正常 API 请求同时在途未达标 | 实测峰值 33；报告已如实披露，但相应硬门槛未通过 |

## 1. P1：引擎臂没有采用相同的 `cn` 身份口径

agent 臂对每个预测 SMILES 调 `cn_identity`，引擎臂则直接读取 `entry.product_identity` 与 `gold_ids` 比较，见 [`exam.py`](/Volumes/CC/Enzyme_Agent/dependingv43/src/pathway_v43/exam.py:510)。引擎答卷生成时也优先沿用引擎返回的 `product_identity`，没有重新计算 `cn_identity(product_smiles)`，见 [`exam.py`](/Volumes/CC/Enzyme_Agent/dependingv43/src/pathway_v43/exam.py:172)。实际记录中的该字段保留了电荷；金标集合则已按 `cn` 归一化。因此两臂不是同一判分口径。

审查时使用封存的 agent 答卷、引擎 Top-10 和题卷金标，统一对两臂原始候选 SMILES 调用本仓 `cn_identity`，再按报告原有的“整条候选 SMILES 匹配”方式计分。引擎成绩从报告中的 **82/117/135/153** 变成 **118/174/193/209**（hit@1/3/5/10）；有 68 题的引擎 rank 发生变化。agent 的 **116/128/130** 不变。按此计分口径，hit@1/3/5 的 agent−engine 差值应为 **−2/−46/−63 题**，而非报告中的 **+34/+11/−5 题**。

上面是身份字段修正后的同口径重算，**仍将每条含点号的 SMILES 当作一个完整候选**。多组分候选的计分口径另见 §4，组件级数字不应与此组数值混用。

现有测试没有覆盖这个问题：合成引擎样例将 `product_identity` 预先设成 `cn_identity(...)` 的结果，见 [`test_exam.py`](/Volumes/CC/Enzyme_Agent/dependingv43/tests/test_exam.py:182)。建议 scorer 忽略引擎传入的身份缓存，统一从原始 `product_smiles` 计算身份；或在写入引擎结果时明确定义并校验 `product_identity` 必为 `cn`。

## 2. P1：“完整候选池”分档只有 Top-10 数据

引擎臂执行 `engine.predict(..., top_k=10)`，再把返回项逐一加进 `pool_identities`，见 [`exam.py`](/Volumes/CC/Enzyme_Agent/dependingv43/src/pathway_v43/exam.py:169)。因此保存的 `pool_identities` 不是完整候选池，只是 Top-10 的身份列表。

报告中的“Top-10 外但池内 0 题、池内无金标 145 题”不能由当前引擎产物支持。应重新导出完整候选池并用统一 `cn` 口径重评；如果不重跑，应将该诊断改称“Top-10 命中／Top-10 未命中”，删除完整候选池相关结论。

## 3. P1：AtomTool 拒绝了有效的键级变化类编辑

从 Chenyu 原始结果逐题核对，51 条空答由 **28 条 abstained** 与 **23 条 rejected** 构成：27 条 abstained 停在 `awaiting_prediction`，另 1 条 abstained 对应 `budget_exhausted`；23 条 rejected 均停在 `awaiting_prediction`。这与报告中的 50 条 `awaiting_prediction` 加 1 条 `budget_exhausted` 对应。

23 条 rejected 中，20 条包含 `bond_already_present`，3 条包含 `unknown_atom`。抽查到的甾体双键迁移任务中，模型给出的目标 MoleCode 能解析并通过目标结构检查，但编辑引用检查认为在已相连的两个原子间 `form_bond` 属于重复成键。当前检查器只检查原始分子图中的边是否存在，没有支持“将已有单键改为双键”的键级变化操作，见 [`atom_tool.py`](/Volumes/CC/Enzyme_Agent/dependingv43/src/pathway_v43/services/atom_tool.py:271)。现有测试还将“已有连接时拒绝 `form_bond`”固定为预期行为，见 [`test_atom_tool.py`](/Volumes/CC/Enzyme_Agent/dependingv43/tests/test_atom_tool.py:100)。

这是一处模型输出协议与 AtomTool 门禁之间的实现缺口，不应通过放松确定性校验解决。修复时应明确定义键级变化编辑，按编辑顺序检查状态转移，并加入“单键升双键、双键降单键”测试。未知原子 ID 的 3 条拒绝另做提示/映射诊断。

另有 28 条模型显式弃答。当前报告没有列出这些题的模型理由、候选映射和证据来源；需要从逐题 prediction artifacts 汇总后再判断哪些是合理弃答、哪些是模型提示或路由问题。报告所记 5 次传输失败不足以解释所有空答：空答与 abstain/rejected 数量逐题核对相符。

## 4. P2：预测和金标的多组分匹配单位需要冻结

首跑 agent 答卷中有 **18 条候选 SMILES 含点号**，代表一条候选中包含多个不相连分子片段。题卷提取器将产物侧按组分拆成 `products_smiles` 列表；当前 scorer 却对整条预测 SMILES 求一次 `cn_identity` 后与单个金标组分比较。现有合成测试覆盖了“多个金标”的情形，但没有覆盖“一个预测字符串含多个组分”的情形。

仅作口径敏感性分析：若将每条候选拆成组分，并以任一预测组分命中任一金标组分作为该候选命中，则 agent hit@1/3/5 为 **129/141/143**，引擎 hit@1/3/5/10 为 **132/184/199/214**。这些是探索性重算，**不是正式结果**。发布修正版前须先明确：一个含多组分的预测候选是否应以其中任一含碳组分命中金标；若应，则命中 rank 按候选 rank 计还是按拆分后的分子 rank 计。随后对两臂用同一规则重评分并补上回归测试。

## 5. 结果宽度、报告完整度与验收状态

- agent 每题实际报告的候选数量分布为：**0 个 51 题、1 个 197 题、2 个 1 题、3 个 1 题、4 个 5 题、5 个 43 题**。多数非空答卷只有一个候选，hit@3/5 的排序空间很有限。任务书规定最多五个，并未要求必须填满五个；因此这是表现诊断，不单独判为协议违约。
- 报告及当前评分 JSON 没有给出任务书要求的逐题证据来源、模型模式、拒因、调用数、token、费用与耗时明细。应把这些字段纳入逐题诊断，并对 51 条空答单独汇总拒绝原因。
- 在途并发峰值为 **33**，低于任务书的 40 个正常响应请求同时在途要求。报告已正确标记该项未完全通过；这不解释当前命中率差异。
- 298 个 qid 唯一、答卷与失败题保留在分母等完整性检查通过。本 review 未发现漏题或重复题证据。

## 6. 修正建议与验收判定

1. 保留 v1 scorer 结果和首跑原始答卷，不覆盖；新增 scorer 版本，从两臂的原始 SMILES 统一计算 `cn`，先重算当前封存首跑，无需重新调用 API。
2. 冻结多组分候选的匹配单位；针对 18 条含点号候选复核后，统一重评分两臂并加测试。
3. 若保留“完整候选池”三档，重新导出真正的完整候选池；否则从报告中移除池外／池内归因。
4. 单独修复 AtomTool 键级编辑协议，对 23 条拒绝逐题分类；任何再次调用模型的批次都标记为 post-hoc，不能覆盖本次首跑。
5. 更新报告，附空答逐题归因、候选宽度统计、修正后的评分器版本与输入哈希，并如实保留 40 并发门槛未通过的记录。

**最终判定：首跑运行数据保留；当前 `EC298_REPORT.md` 的 agent 对引擎主对比、完整候选池诊断及结果验收均不通过。** 完成统一身份重评分、明确多组分口径并修订诊断后，再审核修正版报告。
